# 为什么要系统看，不盯一个 Kernel

大模型推理性能是模型、框架、Runtime、编译器、Kernel、硬件一起决定的。MoE 和 Dense 在多卡集群上，瓶颈经常不在「某一个 MatMul」，而在整条 Serving 链。

常见来源（拿到新模型时先在脑子里过一遍）：

- Router / Scheduler 和真实请求分布对不上
- KV Cache 把显存打成碎片，或 block 配置浪费容量
- Prefill / Decode 抢同一批计算资源，阶段失衡
- 编译和后端没吃满（图没优化、Kernel 没选对）
- 该融合的算子没融，Launch 太碎
- Cube / Vector（或 GPU Tensor Core / CUDA Core）利用率低
- 通信和计算 overlap 不够，AllReduce / AllGather 露在关键路径上

传统路径仍是：Benchmark → Profiler → 分析 → 改参数或代码 → 再测。这条路没问题，缺的是**固定观察顺序**：否则容易在一个热点上打转，说不清「为什么先动这个、后动那个」。

---

## 优化空间是耦合的

改一处会拖动别处，所以必须分层看，而不是只扫一个参数表：

| 改什么 | 常会连带什么 |
|--------|----------------|
| Batch size / max batched tokens | Kernel Shape、显存、通信占比、TTFT |
| TP / EP | 算子切分、通信体积、单卡计算量 |
| 算子融合 | 计算图、Launch 次数、Runtime 调度空隙 |
| PD 分离 vs 混合 | 路由跳数、KV 传输、两套队列 |

同一套启动参数，换模型规模、上下文长度、请求分布，收益可以完全反过来。同一套融合策略，换 Shape、编译器版本、芯片架构，也可能从加速变成回退。

---

## 所以个人分析要固定三件事

1. **先定场景再看数**：吞吐优先还是时延优先，负载是短请求还是长上下文，硬件是单卡还是多卡通信。
2. **先定位 Bound 再动手**：是算不满、带宽满了、调度空了、通信挡着，还是框架没组成有效 batch。
3. **一次一个假设**：改完立刻对比基线，避免参数、补丁、融合混在一轮里说不清是谁的功劳。
