# 五项关键优化

本目录只总结这五项。材料来自 *ModelArts AI 搜索推理优化系列：Qwen3.5-122B 性能调优实践*，以及后续补的先 D 后 P / 先 P 后 D 时序。每条只记：**问题怎么识别**、**具体怎么改实现**。

场景钉死：XHS 智搜，Qwen3.5-122B-A10B-w8a8，昇腾 A3，PD 分离（纯文本 2P(TP4)1D(TP4DP4)）。栈是 vLLM + vllm_ascend + ascend_vllm。

| # | 优化 | 改的是什么 | 原文收益 |
|---|------|-----------|---------|
| 1 | [先 P 后 D 调度](#1-先-p-后-d-调度) | 首 token 从哪条路径出 | 单并发 TTFT ↓ 70ms+；纯文本再降 20ms+ |
| 2 | [KV batch sync](#2-kv-batch-sync) | 每层 KV 同步粒度 | TTFT 606→531ms（↓75ms） |
| 3 | [细粒度 APC](#3-细粒度-apc) | Hybrid 页对齐下的前缀命中粒度 | TTFT ↓ 10ms+（TP4，前缀命中 1k） |
| 4 | [Prefill Inductor 入图](#4-prefill-inductor-入图) | Prefill 编译路径 | 不定长并发 TTFT ↓ 10ms+ |
| 5 | [MTP 零气泡](#5-mtp-零气泡) | Decode 投机解码同步气泡 | 气泡 5ms+→~1ms，TPOT ↓ 1ms+ |

细稿：先 P 后 D → [11-layerwise-cpcd.md](11-layerwise-cpcd.md)；KV batch sync → [12-kv-batch-sync.md](12-kv-batch-sync.md)；APC → [07-fine-grained-apc.md](07-fine-grained-apc.md)；Inductor → [08-prefill-inductor.md](08-prefill-inductor.md)；MTP → [14-mtp-zero-bubble.md](14-mtp-zero-bubble.md)。

## 1. 先 P 后 D 调度

社区默认是 **先 D 后 P + 分层传输**：Decode 收端 meta 先备好，Prefill 才跑；回给客户端的首 token 来自 Decode。

### 问题怎么识别

把社区时序摊开，TTFT 上有四段不该在「出第一个 token」里的工作：

| 社区步骤 | 识别出的问题 |
|---------|-------------|
| 预处理 + 调度必须等上一轮模型执行完 | 调度串行 |
| 先发 transfer meta：`D.scheduler → RS → P.worker` | Prefill 被 D 的地址/meta 堵住 |
| P 再做一遍预处理，再调度，再 prefill | 预处理做了两次 |
| P 传完 KV **丢掉自己算出的首 token**，Decode 再产一个回客户端 | TTFT 里含一次 Decode；P 的首 token 白算 |

瓶颈不是 KV 带宽，是 **首 token 被焊在 Decode 启动之后**。多模态还要加图预处理，这条链会把后续优化空间堵死。所以必须改调度顺序，不能只调传输。

### 具体怎么改实现

把路径拆成两条：首 token 只走 Prefill；KV / meta 异步交给 Decode。

**TTFT（不经过 Decode）**

```text
请求 → RS → 预处理 → 调度 → prefill
     → P 的 API Server 回首 token 给 RS → 客户端
```

**KV 与 Decode（不挡回包）**

```text
prefill 完成后：KV 传输 与 meta 同步异步执行
D 拉完 cache → decode 后续 token
```

配置：`VLLM_ASCEND_ENABLE_TRANSFER_MM_FEATURES=1`，RS `--infer-mode Layerwise-CPCD`。P 预处理完成后仍可通过 `/v1/metaserver` 带 `kv_transfer_params` 去调度 D，但 **等 D 不再挡首 token**。现场还把「prefill 执行」和「等 decode KV 地址」彻底异步，并改了 PD 配比。

| | 先 D 后 P | 先 P 后 D |
|--|-----------|-----------|
| 谁先握手 | D 先发 meta 到 P | P 先跑 |
| 预处理 | RS 一次 + P 再一次 | 一次 |
| 首 token | Decode 现算；P 的丢掉 | P 直接回客户端 |
| TTFT 含不含 Decode | 含 | 不含 |

## 2. KV batch sync

先 P 后 D 之后，KV 仍按层传：每层 forward 完立刻传，和计算共用 NPU stream。

### 问题怎么识别

对齐用 `Event::record` → `Event::sync`。profiling 对上的不是拷贝慢，是同步太细：

- 每次 `aclrtSynchronizeEvent` 约 **4ms**
- 卡住后续 kernel 下发
- **record→record 的 enqueue 间隙占 84.4%**

48 层每层 sync 一次，光同步墙钟就不可接受。问题定义成 **同步粒度**，不是传输协议。

### 具体怎么改实现

Prefill 侧加 KV buffer：

1. 每层 forward 后把 KV 写入 buffer，**立刻返回**，本层不做 `Event::sync`
2. 每 N 层才 sync 一次，再 `batch_transfer_sync_write` 一次送出 N 层

```text
改前: layer_i compute → record → sync(4ms) → transfer → layer_{i+1}
改后: layer_i compute → write buffer → layer_{i+1}  …  每 N 层才 sync + batch write
```

开关：`VLLM_CLOUD_KV_BATCH_SIZE`，默认 0=禁用。N 越大，下发越连，buffer 越大，D 侧看到 KV 的窗口越粗。不定长并发（2P1D，P: tp4dp1，D: tp4dp4，均长 8k）TTFT 606→531ms。

和先 P 后 D 正交：那条改谁先跑、首 token 从谁出；这条改每层 sync 次数。

## 3. 细粒度 APC

Qwen3.5 是 Hybrid：12 层 Full Attention 用分页 KV，36 层 GDN 用 SSM 状态。APC 要求两类 block 对齐到同一物理页。

### 问题怎么识别

命中的最小前缀长度 ≈ `block_size`，而 `block_size` 被页对齐锁死：

```text
attn_single_token_k_page_size × attn_block_size == ssm_block_page_size

block_size = cdiv(ssm_block_page_size,
                  kernel_block_size × attn_single_token_k_page_size)
```

`attn_single_token_k_page_size` 由模型参数决定，不能改。第二阶段为了 QPS，部署从 **TP8 改到 TP4** 后：

- 单卡 SSM/KV 布局变了
- TP=4 算出 `block_size = 2048`
- 前缀不到 2048 token 就不可能命中 → APC 形同虚设
- TP8 上还能用的 APC，在 TP4 上直接不适配

这是改 TP 连带打出来的，不是一开始就做细粒度。

### 具体怎么改实现

不改注意力，不改 SSM 真页。人为把 attn 侧单 token 页 **记账放大**：

```text
pad_factor = N
attn_single_token_k_page_size' = attn_single_token_k_page_size × N
block_size' = block_size / N
```

N=2：block 2048→1024，最小可共享前缀减半。实现上是多分配「空洞」KV 页，以显存换粒度。`PAD_FACTOR=2` 时 KV 显存大约浪费一半。

开关：`VLLM_ASCEND_KV_CACHE_PAD_FACTOR`，默认 1。对所有 Hybrid（Attention + Mamba/GDN）通用。收益：TP4、前缀命中 1k 时 TTFT ↓ 10ms+。

## 4. Prefill Inductor 入图

Prefill 动态 shape 从几十到几十万，静态图编译产物复用不上。

### 问题怎么识别

先试社区 **Piecewise ACLGraph**，两条都失败：

1. **分档盖不住业务**。bucket 有限（当时提到 8192）。XHS 不定长大量 miss 档位，编译产物复用不上，还多付编译税，实测无收益。
2. **ACLGraph 和通信重叠打架，服务直接崩**。ACLGraph 要求算子同一 NPU stream 顺序执行；`TASK_QUEUE_ENABLE=2`（二级流水）让 HCCL 和计算不同 stream overlap → stream 语义冲突、域错误。

要换一条：能吃动态 shape，又不和多 stream 通信重叠冲突。

### 具体怎么改实现

Prefill（主模型 + MTP）改 `torch.compile` + `torch_npu._inductor`，管线：Dynamo → VllmBackend → Inductor → NPU 算子，替代 ACLGraph。

| 点 | 做法 | 为什么 |
|----|------|--------|
| 管线复用 | 复用 GPU 侧 vLLM 编译管线，只换 NPU backend | 少写一套 |
| `fullgraph=True` | 禁止 graph break | 整条 forward 都在图里才融得满 |
| 反函数化 | 对 `atb._npu_reshape_and_cache`、`atb._npu_rotary_embedding` 等还原原地写 | 编译后 KV/RoPE 语义和 eager 一致 |
| 禁用 Triton | `TORCHINDUCTOR_DISABLE_TRITON=1`，lowering 走 AscendKernel | 不要再生成 Triton kernel |
| Buffer | `allow_buffer_reuse=True`；关掉 `reorder_for_locality` / `reorder_for_peak_memory` | NPU 上那些重排不兼容 |
| 缓存 | `TORCHINDUCTOR_CACHE_DIR` | 重启不重编译 |

开启：删 `--enforce-eager`；`--additional-config '{"ascend_turbo_graph_config":{"enabled":true}}'`；MTP 去掉 `speculative_config.enforce_eager: true`。不定长并发 TTFT ↓ 10ms+，短序列更明显。

## 5. MTP 零气泡

社区主干 [vllm#32951](https://github.com/vllm-project/vllm/pull/32951)，昇腾移植 [vllm-ascend#7640](https://github.com/vllm-project/vllm-ascend/pull/7640)。细稿见 [14-mtp-zero-bubble.md](14-mtp-zero-bubble.md)。

### 问题怎么识别

传统投机解码每 step 要把 `num_accepted_tokens`、`num_computed_tokens` **从设备同步回 CPU**，CPU 改状态、组下一拍 input，NPU 才能启动。profiling 上每个 Decode step 有 **5ms+** 空闲。

0.19.rc1 社区已有零气泡，但 `platform.py` 在「投机解码 + async」上会关掉 async——当时 Ascend 还没有设备侧 `num_computed_tokens` 修正，硬开会精度发散。所以升级本身不亮，要补修正并去掉禁令。

### 具体怎么改实现

**乐观假设 + 异步执行 + 设备端修正**。CPU 先当「上一轮 draft 全接受」往下走，对错在 NPU 上改，不把计数拉回 CPU 再开下一拍。

```text
改前: sample → D2H sync(accepted) → CPU 改状态 → 才能 launch 下一拍
改后: sample → valid_count 留在设备
      下一拍 CPU 按全接受 prepare/launch
      NPU: num_computed = prev_gpu + valid_count（新请求走 CPU 值）
      rejected = prev_drafts + 1 - valid_count
```

设备 kernel：`update_num_computed_tokens_for_batch_change`。CPU 乐观长度用 `correct_optimistic_seq_lens_cpu` 按同一式子减回（昇腾 attention 要 CPU `seq_lens`）。本项目开关 `ENABLE_ZERO_BUBBLE=1`；社区是 `--async-scheduling` + MTP spec config。

气泡 5ms+ → ~1ms，TPOT ↓ 1ms+。对所有 MTP 投机解码通用。

## 五项怎么串在一条链上

```text
请求 → RS 按「先 P 后 D」调度
        │
        ├─ Prefill：Inductor 入图把动态 shape 编进图
        │           细粒度 APC 让 TP4 下前缀能命中
        │           算出首 token 直接回客户端     ← TTFT
        │
        ├─ P→D：KV 不再每层 sync，按 N 层 batch 传
        │
        └─ Decode：拉完 KV 后接后续 token
                   MTP 零气泡把投机解码同步税压到 ~1ms  ← TPOT
```

先 P 后 D 决定首 token 还在不在 Decode 上；batch sync 决定 KV 传的时候算不算得动；APC / Inductor 决定 Prefill 本身快不快、前缀能不能复用；零气泡决定 Decode 每步还被同步卡住多少。
